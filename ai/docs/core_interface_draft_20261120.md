# 地面 AI 核心：对外接口草案

2026-11-20，第 1 稿。只是方案，没有改任何代码。标了"待定"的地方尚未决定。

## 1. 一句话

把算法做成一个独立运行的程序（下面叫"核心"）。使用者每帧把战场情况用消息发给它，它回每辆车该怎么开。核心里没有任何一行和某个具体游戏有关的代码；怎么从游戏里拿到数据、怎么把指令送回去，由使用者自己解决，我们不公开自己的做法。

```
 使用者那一侧（各家自己写，我们的不公开）        公开的部分
┌──────────────────────────┐    消息     ┌──────────────────────────┐
│ 从环境里取车辆、占领点状态 │ ─────────> │ 核心：指挥 → 路线 → 避让 → 驾驶 │
│ 把油门 / 转向送回环境      │ <───────── │ 读地图包（四个文件）            │
└──────────────────────────┘            └──────────────────────────┘
                                                    ↑
                                         地图包生成器（公开"加工"那一半）
```

## 2. 哪些公开，哪些留在私有

| 部分 | 现在在哪 | 处理 |
|---|---|---|
| 驾驶、避让、路线（路线库、路网、临时搜索） | `ground_motion.c`、`ground_motion_library.inc`、`ground_routes.c`、`ground_network.c`、`ground_nav.c` | 公开。这几个文件现在就基本不碰游戏 |
| 指挥（车道方案、区域人数上限、占点后续、后方警报） | `ground_teamplan.inc`、`ground_task_command.inc`、`ground_tactics.inc`，编在 `ground_brain.c` 里 | 公开，但要先从 `ground_brain.c` 里拆出来。这是主要工作量 |
| 取数据、送指令、物理帧率设置 | `ground_brain.c` 其余部分（641 处游戏引用） | 私有，不公开，也不写说明 |
| 火控（选瞄准点、穿深判断、开火时机） | `ground_brain.c` 里 46 个受保护函数 | **待定 A**，见第 8 节。我建议第 1 版不放进核心 |
| 实时射线感知、头顶探测 | `ground_lidar.c`、`ground_overhead.c` | 不放进第 1 版。现在的路线库模式行驶时不用它（拆分时要再确认一次） |
| 地图包生成：从游戏文件里提取 | s42 生成器前半段 | 私有 |
| 地图包生成：从"障碍栅格 + 占领点 + 出生点"加工成四个文件 | s42 生成器后半段 | 公开，连同四个文件的格式说明 |

地图包成品是否分发尚未决定。建议只给生成器和格式，不给做好的包。

## 3. 约定

这些直接沿用核心现在的内部约定，不用改算法：

- 单位：米、秒、弧度、米每秒。
- 坐标：水平面是 x 和 z，y 朝上。朝向 0 指向 +x，正方向朝 +z 转。
- 车辆位置指履带转向中心，不是模型原点。
- 时间：使用者给的毫秒时钟，只要求单调递增。
- 节拍：每秒 24 次。更快也可以，核心按收到的时间算；低于每秒 10 次不保证效果。
- 车辆身份：`id`（整场不变）加 `life`（每次重生加一）。`life` 变了，核心就把这辆车当新车处理。
- 上限：128 辆车、96 条车道、每个出生区 64 个出生位。

## 4. 使用者发给核心的消息

| 消息 | 什么时候发 | 内容 |
|---|---|---|
| 开场 | 一场开始 | 接口版本号；地图包路径；有几支队伍；每个占领点的编号、位置、半径；各队的指挥方式（见第 6 节） |
| 车辆登记 | 一辆车出生或重生 | `id`、`life`、队伍；是否由核心驾驶（玩家的车填否）；车体长、宽、车体中心相对转向中心的偏移；巡航速度、倒车速度；能否原地转向 |
| 车辆注销 | 一辆车被毁或离场 | `id`、`life` |
| 每帧状态 | 每个节拍 | 时间；每辆在场车的位置（x、y、z）、朝向、水平速度（vx、vz）、转向角速度；每个占领点的归属和占领进度；"谁看见了谁"的列表（一方 `id`、另一方 `id`） |
| 外部命令 | 随时 | 见第 6 节 |
| 结束 | 一场结束 | 无 |

说明：

- 玩家的车也要登记和上报。核心不驾驶它，但避让和区域人数统计要算上它。
- "谁看见了谁"由使用者按自己环境的规则给。使用者给不了，可以不发，核心退化成只按距离判断。
- 车体尺寸只在登记时给一次。

## 5. 核心发给使用者的消息

| 消息 | 什么时候发 | 内容 |
|---|---|---|
| 就绪 | 收到开场后 | 地图包是否读成功、读到几条车道和几条路线；失败时给原因 |
| 每帧指令 | 每收到一帧状态回一次 | 对应的时间；每辆由核心驾驶的车：前进 / 后退 / 左 / 右四个开关（和玩家按 W S A D 一样），当前状态（行驶、等车、到达、被堵等），想打的目标 `id`（没有就是 0） |
| 命令回执 | 命令被接受、拒绝、完成、受阻时 | 命令编号、结果、原因（没有路、目标点失效、车辆被毁、被更新的命令取代等） |
| 日志 | 可选 | 文本行，和现在对局日志里的内容一样 |

关于时序：

- 使用者发一帧状态，核心回一帧指令。使用者不应该停下来等：指令没到就沿用上一帧的。
- 一帧指令的有效期是 500 毫秒。过期还没收到新的，使用者应当松开所有按键并刹车。
- 核心输出的是四个开关，不是连续的油门量。这是现在驾驶层的做法（像玩家一样开车），接别的环境时，由使用者把开关映射成自己的操纵量。

## 6. 指挥方式和外部命令（单人任务用这个）

每支队伍在开场时选一种：

- **自动**：现在的做法。核心自己读车道方案、派车、占点后安排后续。
- **外部**：核心不派车。每辆车只执行收到的外部命令，没有命令就原地待着。
- **混合**：默认自动；某辆车收到外部命令后归外部管，直到收到"释放"。

外部命令的种类：

| 命令 | 参数 | 含义 |
|---|---|---|
| 去占点 | 车辆列表、占领点编号 | 走车道进圈占领 |
| 去某处 | 车辆列表、位置、到达半径、（可选）到达后的车头朝向 | 走路网到一个任意位置 |
| 守在某处 | 车辆列表、位置、朝向 | 到位后保持不动、车头对准 |
| 停下 | 车辆列表 | 立刻刹停 |
| 释放 | 车辆列表 | 交还自动指挥（只在混合方式下有意义） |

一条命令发给多辆车时，路线仍由核心分：谁走哪条车道、是否换一条街，由核心按"不扎堆"的规则决定，任务方不用管。这些命令直接对应核心内部已有的命令结构，所以"外部"入口要加的东西不多，主要是跳过自动派车。

## 7. 消息怎么传

- 本机连接（本机网络端口）。一个连接对应一场对局。
- 每条消息：4 字节长度 + 1 字节消息种类 + 内容。数字都是小端，和四个地图包文件的写法一致。
- 30 辆车时，每帧状态约 1.5 KB，每帧指令约 0.3 KB；一来一回的开销估计不到 1 毫秒（没有实测）。
- **待定 B**：内容用固定二进制（我的建议，体积小、两边都不用解析库）还是文本。文本好调试，但每帧要多做解析。

我们自己继续把核心直接编进现在的程序里用，不走消息。消息外壳只是包在同一套核心外面的一层，两种用法跑的是同一份算法。

## 8. 待定的事

- **A. 火控放不放进核心。** 现在的火控要读目标的装甲和部件数据，这些只能从游戏里来，没法写成通用接口。我建议第 1 版核心只给"想打谁"，瞄哪里、何时开火留在使用者那边（我们的留在私有部分）。代价是别人拿到的核心不会自己开炮。
- **B. 消息内容用二进制还是文本。** 见第 7 节。
- **C. 示例。** 公开包里带一个"日志回放"示例：读一场我们已有的对局日志，按接口发给核心，打印核心的指令。它只演示接口怎么用，不能说明行驶效果。要不要带？带的话，日志里的地图坐标也算游戏数据的衍生物，能不能放尚未决定。
- **D. 地图包成品分不分发。** 见第 2 节末尾。

## 9. 如果按这个方案做，顺序是

1. 把指挥层从 `ground_brain.c` 里拆成独立文件，只通过一个"战场状态"结构读数据。行为不变。
2. 把驾驶、路线、指挥合成一个不含 Windows 和游戏引用的库，现在的程序改为调用这个库。行为不变。
3. 加外部命令入口和三种指挥方式。
4. 加消息外壳和日志回放示例。
5. 把生成器的"提取"和"加工"分开，写清中间格式。

每一步的检查：能编译、受保护函数检查的输出和现在一致、四个文件的读取器 0 警告，然后开一局看日志。第 1、2 步改动面最大，应当各自单独进一局游戏确认没有变样，再往下做。

没有做过的事：以上全部。本文里的消息大小和开销是估算。
